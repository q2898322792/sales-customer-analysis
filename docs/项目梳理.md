# 一、项目目标与主要工作

## 1.1 定位与目标

| 项 | 内容 |
|---|---|
| 定位 | 简历中的**第二个项目**（分析向），与「制造业经营分析数据仓库」（工程向）互补 |
| 目标岗位 | 数据分析专员 / 数据仓库 / 数据开发 |
| 核心目标 | 补上第一个项目缺的那一环 —— **从"有数据"到"有结论"** |

第一个数仓项目证明了「能把数据整对、能建链路」，但**没有分析结论**。本项目专门补这块：
拿到数据 → 判断数据能不能支撑结论 → 分层与异常检测 → 输出可执行建议。

## 1.2 五项主要工作

| # | 工作 | 产出 |
|---|---|---|
| 1 | **构造符合真实业务特征的数据集** | `make_data.py` → `data/sales.db`（300 客户 / 353 天 / 79.9 万行订单） |
| 2 | **客户价值分层** | RFM 五分位打分 + 八分层，识别营收主力与流失风险客群 |
| 3 | **聚类交叉验证** | numpy 手写 KMeans（k=4），验证规则分层稳健性 |
| 4 | **经营异常检测** | 稳健 z-score 检出单均金额异常月，定位异常出在"金额维度" |
| 5 | **工程化与交付** | 双数据源架构、一键编排、5 张图 + 2 个 CSV + 8 节报告 |

**为什么第 1 项是"构造数据"而不是"直接用数仓数据"** —— 见第三节结论 5 的说明，
这是本项目最关键的一个判断。

## 2.3 关键关系

- **`config.py` 是唯一的路径/配置来源** → 换机器只需改环境变量，代码不用动
- **`extract.py` 是数据源的唯一抽象层** → 加第三个数据源只需在此加一个内部函数
- **`run_all.py` 是唯一入口** → 单文件跑通全流程，报告模板内嵌其中（不依赖外部模板文件）
- **计算模块（rfm / kmeans / anomaly）互不依赖** → 都可单独 `python xxx.py` 自测
- **`make_data.py` 与 `extract.py` 解耦** → 数据可来自 SQLite 也可来自数仓 MySQL

# 三、业务结论及其依据

## 结论 1：客户结构较为集中 —— Top10 占 31.86%、Top20% 占 61.88%

| | |
|---|---|
| **依据** | 对 300 家客户按累计营收降序排列，计算前 10 名 / 前 20%（60 家）的营收占比（帕累托分析） |
| **数据** | 总营收 158.87 亿元；头部 5 家分别占 8.9% / 5.1% / 3.7% / 3.0% / 2.5% |
| **为什么这样总结** | 集中度是客户经营风险的核心指标。判断阈值取「Top20% ≥ 50%」—— 低于此说明客户结构过于分散（无抓手），高于 80% 则存在单点依赖风险（一个大客户走掉就伤筋动骨）。当前 61.9% 落在"健康但需维护头部"的区间 |
| **行动** | 头部客户配置专属维护；不必过度分散资源去铺长尾 |

> 这条结论的措辞是**程序自动生成**的：`run_all.py` 按集中度是否 ≥50% 自动选择"较为集中"或"高度分散"，避免文字与数字打架。

## 结论 2：「重要价值客户」176 家贡献 86.02% 营收

| | |
|---|---|
| **依据** | RFM 模型：R/F/M 各按五分位打 1~5 分（R 反向，越近越高分），再按各自是否高于均值二分 → 组合成 8 类 |
| **数据** | 重要价值客户 176 家 / 136.66 亿元 / 86.02% / 平均 R=0 天 / 平均 F=3,669 单；一般挽留客户 116 家 / 12.78%；其余四类合计 <1.3% |
| **为什么这样总结** | RFM 是客户价值分析的行业标准模型（R=流失风险、F=粘性、M=贡献）。8 分类的优势是**每一类对应明确的运营动作**：R 高+价值高 → 维护；R 低+价值高 → 召回 |
| **行动** | 重点维护「重要价值/重要保持」；「重要挽留」触达召回 |
| **局限性（如实标注）** | 本数据集的八分层分布不均（176/116/3/3/1/1），因为 R 的离散程度低于 F/M，导致"高于均值"的判定集中在少数组合上。**这是数据特征，不是模型错误** —— 若需要更均衡的分层，应改用 KMeans 或调整阈值 |

## 结论 3：KMeans 聚类与规则分层结论一致（交叉验证）

| | |
|---|---|
| **依据** | 对标准化后的 R/F/M 做 KMeans（k=4，手肘法选 k），与规则八分层对照 |
| **数据** | 高价值 2 家（客均 11.18 亿元）/ 中高 13 家（2.88 亿）/ 中 249 家（0.38 亿）/ 中低 36 家（0.15 亿）；客均营收严格递减 |
| **为什么这样总结** | **单一方法的分层结论不可信**。用"数据驱动"的聚类去验证"规则驱动"的分层，两者结论一致才说明分层稳健。这是分析中的常规做法（交叉验证思路） |
| **技术细节** | 先用 Z-score 标准化再聚类 —— 否则 M（亿元级）会完全支配 R（天数）和 F（单数）的距离度量 |

## 结论 4：2026-06 单均金额异常偏离 +120%（金额维度异常）

| | |
|---|---|
| **依据** | 稳健 z-score：用**中位数 + MAD**（而非均值 + 标准差）算偏离度，阈值 \|z\| ≥ 2.5 **且** 幅度 ≥ 15% |
| **数据** | 月订单量变异系数仅 **0.153**（高度稳定），但单均金额在 18,958 ~ 41,816 元之间波动；2026-06 单均 41,816 元 / 69,751 单 / 偏离 +120.0% |
| **为什么这样总结** | ① **用中位数+MAD 而非均值+标准差** —— 离群值会污染均值和标准差，导致"异常把自己藏起来"；② **加 15% 业务幅度门槛** —— 数据显示金额本身波动极小时 MAD→0，z 值会爆炸（实测曾把 0.2% 的波动判成异常）；③ **对比订单量 CV** —— 订单量稳定而金额剧变，才能断定问题在"金额维度"而不是"交易活跃度" |
| **行动** | 核实是大单/促销的真实业务波动，还是金额字段的质量问题；若是后者，所有营收类指标（营收、客单价、毛利）均失真 |
| **额外价值** | 本数据集的这处异常是**刻意植入的**（2026-06 金额 ×2.2，即 +120%），检测结果与植入值完全吻合 → **相当于给检测方法做了一个带标准答案的测试** |

## 结论 5：本数据集的数据适用性已通过验证（这一步比结论本身更重要）

| | |
|---|---|
| **依据** | 分析前先算 R/F/M 的区分度与营收集中度，与阈值比对 |
| **数据** | R 取值 0~177 天（36 个不同值）✅；F 变异系数 2.08 ✅；M 变异系数 2.09 ✅；Top20% 占 61.9% ✅ |
| **为什么这样总结** | **分层结论的前提是数据本身有区分度**。如果所有客户长得一样，RFM 会把它们随机切开，产出"看起来专业但毫无意义"的 8 个层 |
| **对照案例（关键）** | 姊妹数仓项目用的是**均匀分布**的仿真客户：每客户每天都下单、金额接近。实测 **R 恒为 0、F/M 变异系数仅约 2%、Top20% 仅占 20.6%** —— 用它做 RFM 得到的是「各层营收只差 4%」的**无效分层**。正因如此，本项目**自带构造**了符合真实业务特征的数据 |
| **沉淀的习惯** | **先判断数据能不能支撑结论，再动手分析。** 这条判断过程本身比分层结果更有价值 —— 它区分了"跑了模型"和"做了分析" |

## 结论取舍逻辑速查

| 结论 | 判断依据 | 为什么用这个方法 |
|---|---|---|
| 客户集中度 | 帕累托（累计占比） | 回答"营收是否依赖少数客户" |
| 客户分层 | RFM 八分层 | 回答"该给谁资源、谁在流失" |
| 分层可信度 | KMeans 交叉验证 | 单方法结论不可信，需第二视角 |
| 经营异常 | 稳健 z-score + 业务幅度门槛 | 回答"数字异动是业务问题还是数据问题" |
| 数据适用性 | 区分度 + 集中度指标 | 回答"这套数据配不配做分层" |

# 四、关键知识点、方法与技术

## 4.1 分析方法

| 方法 | 用途 | 关键点 |
|---|---|---|
| **RFM 模型** | 客户价值分层 | R 需反向打分；五分位切分比固定阈值更适应分布 |
| **帕累托分析** | 客户集中度 | 用累计占比曲线，比单看 Top N 更有信息量 |
| **KMeans 聚类** | 分层交叉验证 | **必须先标准化**，否则量纲大的维度支配距离 |
| **手肘法** | 选 k | 看 inertia 的拐点，而非盲目取 k |
| **稳健 z-score（中位数 + MAD）** | 异常检测 | MAD 对离群值免疫，不会被异常值抬高阈值 |
| **变异系数 CV** | 稳定性度量 | 标准差 / 均值，跨量纲可比的波动性指标 |
| **k-means++ 初始化** | 避免随机初始化的坏结果 | 按距离平方概率撒种子点 |

## 4.2 数据构造（本项目的特色）

| 技术 | 目的 |
|---|---|
| **幂律分布** `w ∝ i^(-0.8)` | 让客户规模符合真实业务的长尾特征（Top20% 贡献 ~62%） |
| **活跃度与规模正相关 + 沉睡客群** | 生成 R 维度的差异 —— 只改金额不改购买行为，R 会恒为 0 |
| **植入已知异常** | 给检测方法一个带标准答案的 fixture，验证方法有效性 |
| **固定随机种子 + 确定性映射** | 保证结果可复现 |

## 4.3 工程实践

| 技术 | 说明 |
|---|---|
| **双数据源抽象** | `extract.py` 对外只暴露 `fetch_*`，内部切换 SQLite / MySQL，下游零改动 |
| **SQLite 自带数据** | 项目 `clone` 即可跑，不依赖本地数据库 —— GitHub 项目的加分项 |
| **一键编排** | `run_all.py` 单文件跑通取数→分析→出图→报告 |
| **报告自动生成** | 结论文字**由实测值驱动**（如集中度措辞、适用性判定），避免文字与数字脱节 |
| **配置集中** | 连接信息一律读环境变量，路径集中在 `config.py` |
| **函数级自测** | 每个模块带 `if __name__ == "__main__"` 自测入口 |

## 4.4 已知局限（面试可主动说）

1. **八分层分布不均**（176/116/3/3/1/1）—— R 的离散度低于 F/M 所致，可改用 KMeans 或调整阈值
2. **数据为仿真构造**，非真实业务数据 —— 已在报告与 README 中明确标注
3. **`--source mysql` 路径下分层无意义** —— 数仓数据的客户是同质的（R 恒为 0），该路径仅用于演示工程衔接
4. **无时序预测** —— 12 个月的数据量做预测偏少，未纳入本期范围
