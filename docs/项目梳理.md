# 一、项目目标与主要工作

## 1.1 定位与目标

| 项 | 内容 |
|---|---|
| 定位 | 简历中的**第二个项目**（分析向），与「制造业经营分析数据仓库」（工程向）互补 |
| 目标岗位 | 数据分析专员 / 数据仓库 / 数据开发 |
| 核心目标 | 补上第一个项目缺的那一环 —— **从"有数据"到"有结论"** |

第一个数仓项目证明了「能把数据整对、能建链路」，但**没有分析结论**。本项目专门补这块：
拿到数据 → 判断数据能不能支撑结论 → 分层与异常检测 → 输出可执行建议。

## 1.2 五项主要工作

| # | 工作 | 产出 |
|---|---|---|
| 1 | **构造符合真实业务特征的数据集** | `make_data.py` → 项目内 SQLite 数据集（客户数 / 天数 / 产品数可调参） |
| 2 | **客户价值分层** | RFM 五分位打分 + 八分层，识别营收主力与流失风险客群 |
| 3 | **聚类交叉验证** | numpy 手写 KMeans，验证规则分层的稳健性 |
| 4 | **经营异常检测** | 稳健 z-score 检出单均金额异常月，定位异常出在"金额维度" |
| 5 | **工程化与交付** | 双数据源架构、一键编排、图表 + CSV + 分节报告 |

**为什么第 1 项是"构造数据"而不是"直接用数仓数据"** —— 见第三节结论 5 的说明，
这是本项目最关键的一个判断。

## 2.3 关键关系

- **`config.py` 是唯一的路径/配置来源** → 换机器只需改环境变量，代码不用动
- **`extract.py` 是数据源的唯一抽象层** → 加第三个数据源只需在此加一个内部函数
- **`run_all.py` 是唯一入口** → 单文件跑通全流程，报告模板内嵌其中（不依赖外部模板文件）

- **`make_data.py` 与 `extract.py` 解耦** → 数据可来自 SQLite 也可来自数仓 MySQL

# 三、业务结论及其依据

> 本节说明**每条结论怎么来的、为什么这样做**；**具体数值见报告对应章节**。

## 结论 1：客户结构较为集中

| | |
|---|---|
| **依据** | 对全部客户按累计营收降序排列，计算前 10 名 / 前 20% 的营收占比（帕累托分析）。→ 报告第一节、第三节 |
| **为什么这样总结** | 集中度是客户经营风险的核心指标。判断阈值取「Top20% ≥ 50%」—— 低于此说明客户结构过于分散（无抓手），高于 80% 则存在单点依赖风险（一个大客户走掉就伤筋动骨） |
| **实现细节** | 这条结论的**措辞是程序自动生成的**：`run_all.py` 按集中度是否 ≥ 50% 自动选择"较为集中"或"高度分散"，从机制上避免文字与数字打架 |
| **行动** | 头部客户配置专属维护；不必过度分散资源去铺长尾 |

## 结论 2：营收高度集中在头部分层

| | |
|---|---|
| **依据** | RFM 模型：R/F/M 各按五分位打 1~5 分（R 反向，越近越高分），再按各自是否高于均值二分 → 组合成 8 类。→ 报告第三节 |
| **为什么这样总结** | RFM 是客户价值分析的行业标准模型（R=流失风险、F=粘性、M=贡献）。8 分类的优势是**每一类对应明确的运营动作**：R 高+价值高 → 维护；R 低+价值高 → 召回 |
| **前提** | 必须先验证数据是否有区分度 —— 见结论 5。否则 8 个类只是把同质客户随机切开 |
| **行动** | 重点维护「重要价值/重要保持」；「重要挽留」低成本触达 |

## 结论 3：KMeans 聚类与规则分层独立互证

| | |
|---|---|
| **依据** | 对标准化后的 R/F/M 做 KMeans（手肘法选 k），与规则八分层对照。→ 报告第四节 |
| **为什么这样总结** | **单一方法的分层结论不可信**。用"数据驱动"的聚类去验证"规则驱动"的分层，两者指向同一结论才说明分层稳健 |
| **一致性的判定口径** | 两种方法的**分层粒度本就不同**（8 类 vs 4 簇），因此不强求成员一致，而是看**价值序是否一致** + **头部营收集中度是否指向同一结论** |
| **技术细节** | ① 先用 Z-score 标准化再聚类 —— 否则 M（金额量级）会完全支配 R（天数）与 F（单数）的距离度量；② 簇的**命名依据是客均营收**而非合计，否则会出现"高价值簇的合计低于中高价值簇"的误导性排列 |

## 结论 4：单均金额异常（金额维度）

| | |
|---|---|
| **依据** | 稳健 z-score：用**中位数 + MAD**（而非均值 + 标准差）算偏离度。→ 报告第二节 |
| **为什么这样总结** | ① **用中位数+MAD 而非均值+标准差** —— 离群值会污染均值和标准差，导致"异常把自己藏起来"；② **必须叠加业务幅度门槛** —— 数据本身极稳定时 MAD→0、z 值会爆炸（实测曾把 0.2% 的波动误判为异常）；③ **对比订单量变异系数** —— 订单量稳定而金额剧变，才能断定问题在"金额维度"而不是"交易活跃度" |
| **行动** | 核实是业务波动还是字段质量问题；若是后者，所有营收类指标（营收、客单价、毛利）均失真 |
| **额外价值** | 数据集里的异常是**刻意植入的**，检测结果与植入值吻合 → 相当于给检测方法做了一个**带标准答案的测试** |

## 结论 5：数据适用性验证（这一步比结论本身更重要）

| | |
|---|---|
| **依据** | 分析前先算 R/F/M 的区分度与营收集中度，与阈值比对。→ 报告第七节 |
| **为什么这样总结** | **分层结论的前提是数据本身有区分度**。如果所有客户长得一样，RFM 会把它们随机切开，产出"看起来专业但毫无意义"的 8 个层 |
| **对照案例（关键）** | 姊妹数仓项目用的是**均匀分布**的仿真客户：每客户每天都下单、金额接近 → 用它做 RFM 得到的是「各层营收几乎没有差异」的**无效分层**。正因如此，本项目**自带构造**了符合真实业务特征的数据 |
| **沉淀的习惯** | **先判断数据能不能支撑结论，再动手分析。** 这条判断过程本身比分层结果更有价值 —— 它区分了"跑了模型"和"做了分析" |

## 结论取舍逻辑速查

| 结论 | 判断依据 | 为什么用这个方法 |
|---|---|---|
| 客户集中度 | 帕累托（累计占比） | 回答"营收是否依赖少数客户" |
| 客户分层 | RFM 八分层 | 回答"该给谁资源、谁在流失" |
| 分层可信度 | KMeans 交叉验证 | 单方法结论不可信，需第二视角 |
| 经营异常 | 稳健 z-score + 业务幅度门槛 | 回答"数字异动是业务问题还是数据问题" |
| 数据适用性 | 区分度 + 集中度指标 | 回答"这套数据配不配做分层" |

# 四、关键知识点、方法与技术

## 4.1 分析方法

| 方法 | 用途 | 关键点 |
|---|---|---|
| **RFM 模型** | 客户价值分层 | R 需反向打分；五分位切分比固定阈值更适应分布 |
| **帕累托分析** | 客户集中度 | 用累计占比曲线，比单看 Top N 更有信息量 |
| **KMeans 聚类** | 分层交叉验证 | **必须先标准化**，否则量纲大的维度支配距离 |
| **手肘法** | 选 k | 看 inertia 的拐点，而非盲目取 k |
| **稳健 z-score（中位数 + MAD）** | 异常检测 | MAD 对离群值免疫，不会被异常值抬高阈值 |
| **变异系数 CV** | 稳定性度量 | 标准差 / 均值，跨量纲可比的波动性指标 |
| **k-means++ 初始化** | 避免随机初始化的坏结果 | 按距离平方概率撒种子点 |

## 4.2 数据构造（本项目的特色）

| 技术 | 目的 |
|---|---|
| **混合分布**（对数正态主体 + 对数正态头部） | 让客户规模呈真实业务的长尾特征，同时避免头尾差距过悬殊把图表压平 |
| **泊松过程**（指数分布购买间隔）+ 沉睡客群 | 生成 R 维度的差异 —— 只改金额不改购买行为，R 会恒为 0 |
| **客单价与规模弱相关**（而非同比例） | 否则 M 会退化成 F 的重复，RFM 白白浪费一个维度 |
| **植入已知异常** | 给检测方法一个带标准答案的 fixture，验证其双向识别能力 |
| **固定随机种子 + 确定性映射** | 保证结果可复现 |

## 4.3 工程实践

| 技术 | 说明 |
|---|---|
| **双数据源抽象** | `extract.py` 对外只暴露 `fetch_*`，内部切换 SQLite / MySQL，下游零改动 |
| **SQLite 自带数据** | 项目 `clone` 即可跑，不依赖本地数据库 —— GitHub 项目的加分项 |
| **一键编排** | `run_all.py` 单文件跑通取数→分析→出图→报告 |
| **报告结论由实测值驱动** | 关键数字与措辞都从计算结果生成，避免文字与数字脱节 |
| **配置集中** | 连接信息一律读环境变量，路径集中在 `config.py` |
| **函数级自测** | 每个模块带 `if __name__ == "__main__"` 自测入口 |

## 4.4 已知局限（面试可主动说）

1. **数据为仿真构造**，非真实业务数据 —— 已在报告与 README 中明确标注
2. **`--source mysql` 路径下分层无意义** —— 数仓数据的客户是同质的（R 恒为 0），该路径仅用于演示工程衔接
3. **无时序预测** —— 数据时长做预测偏少，未纳入本期范围
4. **RFM 八类的客均营收总体递减但非严格单调** —— 样本量小的类别会交叉，属小样本正常现象
